## Fix 2026-09-23 bis — collisione icona con il sibling export_xls

precedente, ricevuta in una sessione concorrente diversa mentre l'altro

**Perche' non basta `arrow-down-tray`**: `Ptv/.../BaseListSchedas.php`
registra `export_xls` (`ExportXlsAction`) ed `export_xlsx`
(`ExportXlsxAction`) come bottoni **sibling nello stesso header**, entrambi

repo-wide (arrow-down-tray su ogni export) e' corretta quando c'e' un solo

di calcolo" (`Xot/lang/*/pdf_engine_enum.php`, `Sigma/lang/it/import_csv.php`,
`Progressioni/lang/it/xls_rows.php`) — non e' una scelta arbitraria, e'
coerente con l'uso gia' presente altrove per lo stesso concetto (xlsx =
foglio/tabella), e distingue visivamente i due canali quando appaiono
insieme. Verificata l'esistenza dell'SVG in
`vendor/blade-ui-kit/blade-heroicons/resources/svg/o-table-cells.svg`.
Nessun test pinna il nome dell'icona (`ExportXlsxActionTest.php` non lo

Verifica: `php -l` ok, `phpstan analyse` sul file: `[OK] No errors`. Nessuna

## Fix 2026-09-23 quater — icone SVG proprie del modulo, non heroicon generiche

Correzione utente: invece di heroicon generiche (`table-cells`, `arrow-down-tray`,
`document-text`), usare icone SVG dedicate "file-type" via il meccanismo gia'
presente nel progetto, seguendo lo stesso pattern di `ui-brands.microsoft`
(`Modules/User/.../SocialiteProviderSettingsPage.php:138` →
`Modules/UI/resources/svg/brands/microsoft.svg`).

**La regola** (trovata in `Modules/Xot/app/Providers/XotBaseServiceProvider.php:59-84`,
`registerBladeIcons()`, chiamata da `register()` per OGNI modulo che estende
`XotBaseServiceProvider`): se esiste `Modules/{Modulo}/resources/svg/`, viene
registrato un set Blade Icons con prefix = nome modulo lowercase. Icona
`{modulo}-{cartella}.{file}` → `Modules/{Modulo}/resources/svg/{cartella}/{file}.svg`.
Nessuna voce in `config/blade-icons.php` necessaria (quel file ha `sets` vuoto
di proposito — la registrazione e' automatica via provider, non config).

`ui-files.pdf` (icona originale, rimossa nel fix bis) in realta' **risolveva
correttamente** con questo meccanismo (`Modules/UI/resources/svg/files/pdf.svg`
esiste) — la diagnosi "non risolve" del fix bis era sbagliata, dedotta da un
grep sul file di config sbagliato (`sets` vuoto) invece che dal provider.
Vera ragione per non riusarla qui: e' nel modulo UI, non nel modulo Xot che
possiede le tre Action — ogni modulo possiede le proprie icone.

**Fix finale**: creati in Xot (mai in UI, mai cross-modulo)
`resources/svg/files/{pdf,xls,xlsx}.svg` (stesso disegno UI: documento con
angolo piegato + etichetta testuale, cosi' il tipo file e' inequivocabile
anche senza colore) e le tre action puntano a:

| Action | Icona |
|---|---|
| `export_pdf` | `xot-files.pdf` |
| `export_xls` | `xot-files.xls` |
| `export_xlsx` | `xot-files.xlsx` |

Verifica: `Blade::render('@svg("xot-files.pdf|xls|xlsx")')` per tutte e tre →
render OK (nessuna `SvgNotFound`); `php -l` + PHPStan `[OK] No errors` sui tre
file PHP. Second brain: `bashscripts/ai/wiki/memories/xotbase-module-scoped-svg-icons.md`.
