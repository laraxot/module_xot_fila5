# 5.221 — un'icona per formato, non un'icona generica

## Richiesta (utente, 2026-09-23)

Sull'icona di `ExportPdfAction` (`heroicon-o-document-text` al momento della
richiesta): "potevi fare `->icon('xot-files.pdf')` e creare
`laravel/Modules/Xot/resources/svg/files/pdf.svg`, cerca di capire la
regola... con la stessa logica puoi migliorare `ExportXlsAction` e
`ExportXlsxAction`".

## La regola (scoperta, non documentata altrove prima d'ora)

`Modules\Xot\Providers\XotBaseServiceProvider::registerBladeIcons()` registra,
per **ogni** modulo la cui ServiceProvider estende `XotBaseServiceProvider`
(quindi tutti), un set blade-icons con prefisso = nome modulo lowercase, path
= `{Modulo}/resources/svg` (se la cartella esiste — skip silenzioso altrimenti).

`BladeUI\Icons\Factory::svg($name)`:
1. `splitSetAndName()` — tutto prima del primo `-` e' il prefisso set (qui il
   nome modulo, es. `xot`), il resto e' il "name".
2. `getSvgFromPath()` — `str_replace('.', '/', $name)` converte i punti in
   separatori di cartella prima di appendere `.svg`.

Risultato: `xot-files.pdf` → prefisso `xot` → name `files.pdf` → file
`Modules/Xot/resources/svg/files/pdf.svg`. Stessa cosa per qualunque modulo:
`ui-files.pdf` → `Modules/UI/resources/svg/files/pdf.svg` (gia' esistente,
usato come riferimento di stile per questa story).

Conseguenza pratica: un'azione che vive in un modulo dovrebbe avere la sua
icona SVG **nello stesso modulo** (`xot-files.*` per azioni Xot), non pescare
da un altro modulo (`ui-files.*`) ne' ripiegare su un heroicon generico
quando serve comunicare un formato file specifico — coerente con
[[componente-riutilizzabile-porta-la-sua-logica]] del second brain: il
componente porta anche la sua icona.

## Perche' non un heroicon

Heroicons non ha icone per formato file (pdf/xls/xlsx): l'alternativa era
sempre un'icona generica (`document-text`, `table-cells`,
`document-arrow-down`, `arrow-down-tray`...) che comunica "e' un documento" o
"si scarica", mai "e' un PDF" / "e' un Excel". Un'icona SVG propria con
etichetta testuale incorporata (`PDF`, `XLS`, `XLSX`) elimina l'ambiguita' a
colpo d'occhio — miglioramento UX diretto, stesso pattern gia' in uso per
`ui-files.pdf`.

## Cosa cambia

| File | Prima | Dopo |
|---|---|---|
| `Modules/Xot/app/Filament/Actions/Header/ExportPdfAction.php` | `->icon('heroicon-o-document-text')` | `->icon('xot-files.pdf')` |
| `Modules/Xot/app/Filament/Actions/Header/ExportXlsAction.php` | `->icon('heroicon-o-arrow-down-tray')` | `->icon('xot-files.xls')` |
| `Modules/Xot/resources/svg/files/pdf.svg` | assente | creato (stile identico a `ui-files.pdf`, per coerenza visiva) |
| `Modules/Xot/resources/svg/files/xls.svg` | assente | creato |
| `Modules/Xot/resources/svg/files/xlsx.svg` | assente | creato (pronto per `ExportXlsxAction`, vedi sotto) |

`ExportXlsxAction.php` **non toccato in questa story**: al momento dell'edit
era locked (`orchestrator-quality-gates`, task
`fix-exportxlsx-icon-clock-to-arrow-down-tray`, poi confluito nella story
[[5.220-export-xlsx-svg-icon-swap]] che ha impostato
`heroicon-o-document-arrow-down`). Quella scelta precede la richiesta
esplicita dell'utente di usare `xot-files.*` per tutte e tre le action — da
allineare non appena il lock si libera (icona gia' pronta:
`xot-files.xlsx`, file gia' creato e verificato in questa story).

## Verifica

- `php -l` pulito su entrambi i file modificati.
- `SvgExistsAction::execute('xot-files.pdf'|'xot-files.xls'|'xot-files.xlsx')`
  → tutte `true` (verificato via `php artisan tinker`, non per ispezione —
  vedi [[feedback_pest_test_before_done]]).
- `SvgExistsAction::execute('ui-files.pdf')` → `true` (controllo di
  riferimento, conferma che il meccanismo di registrazione e' lo stesso).
