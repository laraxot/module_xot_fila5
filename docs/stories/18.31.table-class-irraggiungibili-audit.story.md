# Story 18.31 — Table class irraggiungibili

## Contesto

Tre casi di doppia Table class sono emersi **per incidente** nel giro di poche ore, ognuno
trovato mentre si lavorava ad altro:

| Caso | Come e' emerso |
|---|---|
| `PesisTable` / `PesosTable` | `ListPageHasTableClassTest` rosso dopo la rimozione di `HasXotTable` da `XotBaseListRecords` |
| `JobBatchesTable` / `JobBatchsTable` | costruendo la tabella di `ListJobBatches` (18.23) |
| `SchedaDipSchedasTable` / `SchedaDipsTable` | un `#[\Override]` orfano che fatalizzava all'autoload |

Tre incidenti per lo stesso pattern significa che il pattern e' diffuso e che nessuno lo
sta misurando. Questa story lo misura.

## La regola che decide chi e' raggiungibile

`XotBaseResource::getTableClass()`:

```php
$name = Str::plural(class_basename(static::getModel()));
$class = static::class.'\Tables\\'.$name.'Table';
```

Il nome si deriva dal **model**, mai dalla Resource. `JobBatchResource` ha model `JobBatch`
→ `JobBatches` → `JobBatchesTable`. `JobBatchsTable` non e' raggiungibile da nessun
percorso: si puo' modificare per ore senza che la pagina cambi.

## Ampiezza misurata (2026-09-08, costruendo la risoluzione reale)

**8 Resource con piu' di una Table class, 8 file irraggiungibili. Zero Resource senza
cartella `Tables/`.**

| Resource | Scelta da `getTableClass()` | Irraggiungibile |
|---|---|---|
| `ActivityResource` | `ActivitiesTable` | `ActivitysTable` |
| `JobBatchResource` | `JobBatchesTable` | `JobBatchsTable` |
| `JobsWaitingResource` | `JobsTable` | `JobsWaitingsTable` |
| `MediaResource` | `MediaTable` | `MediasTable` |
| `ClientResource` | `OauthClientsTable` | `ClientsTable` |
| `OauthClientResource` | `ClientsTable` | `OauthClientsTable` |
| `PersonalAccessTokenResource` | `OauthAccessTokensTable` | `PersonalAccessTokensTable` |
| `TenantResource` | `TenantsTable` | `CustomersTable` |

`FilamentSchemasTablesStructureTest` fallisce oggi proprio su
`Activity/ActivityResource/Tables` («Expected exactly one table class»): il test esisteva,
il rosso c'era, e nessuno lo leggeva — vedi 18.29.

## Le due coppie che sembrano incrociate non lo sono

`ClientResource` sceglie `OauthClientsTable` e `OauthClientResource` sceglie `ClientsTable`:
a prima vista pare uno scambio, e cosi' l'avevo letto. Non lo e'. Ogni Resource prende il
file **nella propria cartella**, con il nome derivato dal proprio model:

- `ClientResource` → model `Modules\User\Models\OauthClient` → `OauthClientsTable`
- `OauthClientResource` → model `Laravel\Passport\Client` → `ClientsTable`

I nomi sono invertiti rispetto alle Resource ma **coerenti con i model**, quindi la
risoluzione e' corretta. Il problema resta il doppione in ciascuna cartella. Da qui una
domanda che questa story deve porre e non presumere: quei nomi di Resource sono giusti?
Una `ClientResource` il cui model e' `OauthClient` e una `OauthClientResource` il cui model
e' `Client` sono due nomi scambiati, e rinominarli e' un lavoro diverso — se si decide, va
in una story a se'.

## Task

1. Per ognuno degli 8: confrontare il corpo di `getTableColumns()` fra il file raggiungibile
   e quello morto. **Il file morto puo' essere il piu' completo**: e' il caso tipico di chi
   ha lavorato sul file sbagliato per ore. Se lo e', il contenuto va portato in quello
   raggiungibile prima di eliminarlo.
2. Eliminare il file irraggiungibile solo dopo il confronto.
3. Verificare che `FilamentSchemasTablesStructureTest` torni verde (chiude un pezzo di 18.29).
4. Estendere quel test da «esattamente una Table class per cartella» a «ogni Table class
   presente e' raggiungibile da `getTableClass()`»: e' l'invariante vera, e vale anche se
   un giorno le cartelle ne contenessero legittimamente due.

## Acceptance criteria

- [ ] 0 Table class irraggiungibili
- [ ] Nessuna colonna persa: per ogni coppia, confronto dei corpi documentato
- [ ] `FilamentSchemasTablesStructureTest` verde
- [ ] La guardia verifica la raggiungibilita', non il conteggio dei file
- [ ] `phpstan analyse Modules` non peggiora

## Nota di metodo

Il confronto fra i due file va fatto sul **corpo del metodo estratto col tokenizer**, non
sulle chiavi grezze del file: due sessioni hanno gia' sbagliato quella misura oggi,
contando `create`/`edit`/`index` di `getPages()` come campi. Vedi il protocollo condiviso
in 18.22.

## Aggiunta — sessione base-ptvx-fila5-92 [6a95f1]

Avevamo scritto la stessa story in parallelo (`18.31.table-class-nome-dal-model-una-sola-raggiungibile`,
ora rimossa). Quella misura è confluita qui; questi sono i pezzi che aggiunge.

### La lettura corretta di Client/OauthClient è la tua

Al primo colpo avevo scritto "le due Resource si sono scambiate la Table class".
È sbagliato: la risoluzione è corretta, ogni Resource prende il file col nome del
proprio model. Sono i **nomi delle due Resource** a essere scambiati rispetto ai
model (`ClientResource` ha model `OauthClient`, `OauthClientResource` ha model
`Laravel\Passport\Client`). Rinominarle è un lavoro diverso e non appartiene a
questa story.

### Le classi astratte accanto alla concreta non sono un problema (5)

`BaseSchedasTable`, `BaseRatingsTable`, `BaseMessagesTable`, `BaseOptionsTable`,
`BaseCriteriEsclusionesTable`: è il pattern Base/concrete del progetto, lo stesso
di `BaseRatingForm`/`RatingForm`. La guardia deve ammetterle **per struttura**
(sono `abstract`), non per nome: un `Base*Table` concreto sarebbe comunque morto.

### Due liste non si aprono per questo motivo, e una ha una causa in più

| Pagina | Errore |
|---|---|
| `Ptv/ListCategoriaPropros` | `Expected a sub-class of "Modules\Xot\Filament\Resources\Tables\XotBaseResourceTable"` |
| `Ptv/ListStabiDirigentes` | `Expected an existing class name. Got: "Modules\Ptv\Filament\Resources\Repor…"` |

La seconda si spiega con un dato che manca sopra: **4 Resource non hanno affatto
la cartella `Tables/`** — `Ptv/AnagResource`, `Ptv/ReportResource`,
`Rating/HasRatingResource`, `Xot/XotBaseResource` (quest'ultima è la classe base,
non una Resource vera). `getTableClass()` compone un nome dentro una cartella che
non esiste e l'`Assert` fallisce. Quindi l'invariante ha due metà: *ogni Table
class presente è raggiungibile* **e** *ogni Resource concreta ne ha una*.

### Il precedente che dice perché un file morto non è innocuo

`IndennitaResponsabilita/SchedaDipResource/Tables/SchedaDipSchedasTable.php`,
rimosso il 2026-09-08. Era irraggiungibile da sempre (`getTableClass()` risolve
`SchedaDipsTable`), quindi apparentemente inerte. Quando la classe base ha perso
`getSchedaTypeFilterModelClass()`, il suo `#[\Override]` orfano è diventato un
**fatal error all'autoload** e la lista `SchedaDip` ha smesso di aprirsi.

Una classe irraggiungibile non è dead code tranquillo: è una mina che esplode al
primo refactor della base, e che nessun test trova finché qualcosa non la carica.
Motivo in più per chiudere questa story prima di 18.24 e 18.26, che di refactor
sulle basi ne fanno parecchi.

### Aggiunta agli acceptance criteria

- [ ] Ogni Resource concreta ha una cartella `Tables/` con dentro la classe che
      `getTableClass()` risolve (oggi 4 non ce l'hanno)
- [ ] La guardia ammette le `abstract` per struttura, non per prefisso del nome
- [ ] Nessun `#[\Override]` orfano nelle Table class rimaste
