# Story 5.92 — Migrazione docs/chat → BMAD stories

## Filosofia / Zen / Perché / Religione

**Perché eliminare `docs/chat`:**

`docs/chat` è nato come canale informale per coordinamento multi-agente (claim, STOP, handoff). È diventato:
- **Single point of truth orale** invece che strutturato
- **Non versionato come storie** — non ha AC, non ha definition of done, non ha ownership chiaro
- **Non queryabile** — grep su `docs/chat/` non scala, non si collega a sprint-status.yaml
- **Duplicazione di sforzo** — ogni claim/STOP dovrebbe essere una story BMAD con AC, task, dev notes, references

La governance BMAD (story, epic, sprint-status, definition of ready/done) esiste proprio per sostituire i "chat file" con artefatti tracciabili. Mantenere entrambi è **waste** (muda).

**Perché BMAD stories:**

- Ogni claim → `story` con `status: in-progress | ready-for-dev | review | done`
- Ogni STOP → `story` con `category: blocker` o `risk`, AC = "rischio mitigato / incidente risolto"
- Ogni handoff → `story` con `type: handoff` e `references` ai documenti passati
- Tutto finisce in `sprint-status.yaml` → visibilità, metriche, retrospettive
- `bmad-create-story` forza analisi (epic, architecture, UX, previous story, git intelligence)

**Regola d'oro:** *Se vale la pena scriverlo in docs/chat, vale la pena farne una BMAD story. Se non vale una story, non vale nemmeno docs/chat.*

## Visione / Scopo / Logica

- **Visione:** zero file in `docs/chat/` creati dopo questa story; tutto il coordinamento passa per BMAD stories
- **Scopo:** migrare i pattern `claim-*`, `STOP-*`, `handoff-*` esistenti in storie BMAD appropriate; aggiornare AGENTS.md, standing order, BOOTSTRAP, MCP config per puntare a BMAD
- **Logica:** mappare 1:1 i tipi di file `docs/chat` → tipi di story BMAD; creare story per i casi aperti; deprecato docs/chat nel README e trigger map
