# Story 18.32 — `docs/chat/`: la data sta nel documento, non nel nome

## Il fatto

`docs/wiki/rules/docs-chat-filename-no-dates.md` vieta le date nei nomi dei file di
`docs/chat/` — in qualunque posizione, prefisso, mezzo o coda, con esempi espliciti. Il
2026-09-08 la violano **96 file su 165**.

La regola non e' ignota: e' scritta, ha una skill dedicata
(`bashscripts/ai/wiki/skills/docs-chat-filename-no-dates.md`) e compare nel catalogo. Non
aveva pero' nessuna guardia, e una regola senza guardia si applica solo quando chi scrive
se la ricorda.

## Perche' la data nel nome fa danno

Non e' estetica:

- `git log --follow` e `git blame` diventano inutili sul tema: due file per lo stesso
  argomento a due giorni di distanza invece di un file con due sezioni;
- il raggruppamento per argomento si rompe: `claim-hasxottable-...-2026-09-01.md` e
  `claim-hasxottable-...-2026-09-08.md` non stanno vicini a colpo d'occhio;
- la data e' **gia'** nel git history, quindi e' duplicazione che invecchia male: il file
  aggiornato oggi porta nel nome la data in cui e' nato.

## Guardia messa oggi

`Modules/Xot/tests/Unit/Docs/ChatFilenameNoDatesTest.php`, a **tetto decrescente**: non
pretende zero (bloccherebbe il repo su una bonifica di 96 file), fissa una costante che
puo' solo scendere. Un file nuovo con la data fa fallire il test; chi ne rinomina uno
abbassa la costante.

Un secondo test verifica che il tetto resti allineato al debito reale: se la bonifica
procede e la costante non scende, il test tornerebbe verde per inerzia e smetterebbe di
misurare qualcosa.

Verificato: aggiungendo un file con la data il primo test fallisce, rimuovendolo torna verde.

## Task

1. Rinominare i 96 file in kebab-case senza data, spostando la data in una riga del
   documento (`<!-- Aperto il ... -->` o frontmatter).
2. Aggiornare i link interni: `grep -rn "<nome-vecchio>" --include='*.md'` prima di ogni
   rename, perche' i file di `docs/chat/` si citano fra loro.
3. Abbassare `CHAT_FILES_WITH_DATE_BASELINE` a ogni lotto.
4. Portarla a `0` e trasformare il primo test in un'asserzione secca quando il debito e'
   chiuso.

Il rename va fatto con `git mv`, non copia-e-cancella: altrimenti si perde la storia del
file, che e' esattamente il valore che questa regola vuole proteggere.

## Attenzione: file di coordinamento vivi

Molti dei 96 sono claim e STOP che **altre sessioni stanno leggendo e scrivendo adesso**.
Rinominarne uno mentre un'altra sessione ci scrive dentro produce due file. Il rename va
annunciato in `docs/chat/` prima, o fatto su file la cui conversazione e' chiusa.

## Acceptance criteria

- [ ] 0 file con data nel nome in `docs/chat/`
- [ ] Nessun link interno rotto (`grep` dei nomi vecchi a zero risultati)
- [ ] `CHAT_FILES_WITH_DATE_BASELINE` a 0 e primo test convertito in asserzione secca
- [ ] Ogni rename fatto con `git mv`
