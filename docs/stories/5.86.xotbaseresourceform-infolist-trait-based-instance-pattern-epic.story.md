# 5.86 — Unificare Form/Infolist al pattern istanza già usato da Table

## Richiesta utente (verbatim, tradotta in task)

1. `XotBaseResourceTable.php` usa già `use HasXotTable;` + pattern istanza
   (`app(static::class)` in `configure()`). L'utente chiede di valutare la rimozione
   di `use TransTrait;` da lì perché "c'è già dentro HasXotTable" — **premessa
   verificata e falsa** (vedi sotto), non eseguita as-is.
2. `XotBaseResourceForm.php` dovrebbe fare `use HasXotForm;`, usare
   `$instance = app(static::class);`, e i metodi come `getFormSchemaColumns()`
   dovrebbero diventare non statici, spostati dentro `HasXotForm`.
3. Stessa logica replicata in `XotBaseResourceInfolist.php` con `HasXotInfolist`.
4. `HasXotForm::form()` deve fare `->columns($this->getFormColumns())`, non
   `->columns(2)` hardcoded — **già corretto nel working tree** (fix non committato
   del batch-04, story 5.83, 2026-09-07 ~23:00), l'utente lo vedeva rotto guardando
   HEAD/GitHub, non il disco locale.

## Verifica delle premesse (pillar 3 standing order)

- **TransTrait non è dentro HasXotTable.** Controllata l'intera catena
  (`HasXotTable` → `use HasTableLayoutPage` → `use TableLayoutTrait`): nessuna
  include `TransTrait`. `HasXotTable::getTableHeading()` usa un meccanismo diverso
  (`GetTransKeyAction`), non sostituibile 1:1 con `TransTrait::trans()`.
- **`TransTrait` ha un solo consumer reale rimasto**: `static::trans('buttons.history')`
  in `Modules/Job/app/Filament/Resources/ScheduleResource/Tables/SchedulesTable.php:48`.
  Rimuoverlo da `XotBaseResourceTable` senza migrare quel call site rompe
  `SchedulesTable`. Verificato indipendentemente anche da sessione `-ad` (converge).
- **Blast radius della richiesta 2+3 è enorme**: `git grep -l "extends
  XotBaseResourceForm"` → **143 classi**, di cui **142 con `static function
  getFormSchema()`**; `extends XotBaseResourceInfolist` → **137 classi**, tutte
  e 137 con `static function getInfolistSchema()`. Totale **279 file**.
- **Vincolo strutturale PHP**: un trait con `abstract public function
  getFormSchema(): array` (istanza) non può essere implementato da una sottoclasse
  che lo dichiara `static` — è lo stesso errore fatale già risolto oggi nelle story
  5.83/5.85 (`#[\Override] ... but no matching parent method exists` /
  "Cannot make non static method abstract static"), qui moltiplicato per 279 file.
  **Non è un refactor incrementale file-per-file**: la classe base e i 279
  consumer devono cambiare in un'unica finestra coerente, o serve un bridge a due
  nomi (vedi Piano).

## Stato attuale (verificato sul codice, non sulla documentazione)

| Classe | Pattern | Nota |
|---|---|---|
| `XotBaseResourceTable` | **istanza**, `use HasXotTable; use TransTrait;` | già target-pattern; `configure()` fa `app(static::class)->table($table)` |
| `HasXotTable` (trait) | istanza | maturo, ~150 consumer, nessun problema noto |
| `HasXotForm` (trait) | istanza, `getFormSchema()` abstract, `getFormColumns()` overridabile (default 2), `form()` final | **corretto ma trait.unused**: nessuna classe lo consuma ancora |
| `XotBaseResourceForm` | **tutto statico** | `configure()`, `getFormSchemaColumns()` (default 1, non 2 — divergenza col trait), `getFormSchema()` (bridge vuoto), più helper statici per Wizard (`getSteps()`, `getStepByName()`, `optionLabelFromRecord()`) |
| `HasXotInfolist` (trait) | istanza, `infolist()` final, `getInfolistColumns()` default 2 | **trait.unused**, PHPStan lo segnala (finding aperto, story 5.85 lo ha deliberatamente non toccato) |
| `XotBaseResourceInfolist` | **tutto statico**, `abstract` | `configure()` final static, `getInfolistSchema()` abstract static |

## Piano (bridge a due nomi, forward-only, zero flag-day su 279 file)

Non si rinomina né si rompe nulla in un colpo solo. Si introduce il nuovo pattern
**accanto** al vecchio, poi si migra a piccoli lotti (stesso schema riuscito oggi su
5.83/117 file e 5.85/38 file), infine si rimuove il vecchio quando l'ultimo consumer
è migrato.

1. **Task A (piccolo, sicuro, ora)** — migrare l'unico consumer reale di
   `TransTrait` su Table: sostituire `static::trans('buttons.history')` in
   `SchedulesTable.php` con l'equivalente diretto (`__('job::...')` o quanto
   risolve `TransTrait::trans()` per quella chiave — va tracciata la chiave
   effettiva prima di cambiarla, non indovinata). Poi rimuovere
   `use TransTrait;` da `XotBaseResourceTable`. **Bassissimo rischio, 2 file.**
2. **Task B (bridge)** — in `XotBaseResourceForm`: aggiungere `use HasXotForm;`
   MA senza dichiarare `getFormSchema()` istanza col nome esistente (romperebbe
   le 142 sottoclassi statiche). Il trait espone il metodo abstract con un nome
   nuovo transitorio o la classe fornisce un default che il bridge statico
   `getFormSchema()` continua a chiamare finché esiste una sottoclasse non
   migrata. Analogo al bridge già in produzione
   `getFormSchema()` → `getFormSchemaOld()` su `XotBaseResource` (vedi
   `docs/chat/STOP-xot-getformschema-abstract-senza-bridge-2026-09-02.md`, la
   stessa regressione già successa una volta). Stessa cosa per
   `XotBaseResourceInfolist`/`HasXotInfolist`.
3. **Task C (swarm, grosso)** — migrare i 142 file Form + 137 Infolist da
   `public static function get{Form,Infolist}Schema()` a `public function` (drop
   `static`), verificando per ciascuno che non ci siano altri riferimenti statici
   interni (`self::`/`static::` su quel metodo da altri punti del file). Stesso
   schema di dispatch della story 5.85: batch da ~15-20 file, un agente per
   batch, lock per file, verifica `php -l` + phpstan puntuale, nessun commit per
   agente.
4. **Task D (cleanup)** — quando C è completo al 100%, rimuovere il bridge statico
   da `XotBaseResourceForm`/`XotBaseResourceInfolist`, allineare
   `getFormSchemaColumns()`→`getFormColumns()` (naming, default 1 vs 2 da
   riconciliare con l'utente: quale valore è quello vero? Verificare quanti
   consumer overridano il default prima di scegliere).
