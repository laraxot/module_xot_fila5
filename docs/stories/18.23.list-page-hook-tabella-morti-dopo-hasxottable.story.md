# Story 18.23 — Hook di tabella morti sulle List page

## Contesto

Il commit `23965cd0b` ("XotBaseListRecords senza HasXotTable, la tabella passa
dalla Table class") ha risolto un bug reale e visibile: il `table()` del trait,
composto sulla **pagina**, rifaceva la configurazione con i metodi della pagina e
azzerava quella della Table class — `Table::columns([])` e `Table::filters([])`
resettano, non fanno merge. Prima del commit, sulla lista
`indennita-responsabilitas`: 6 colonne e 3 filtri costruiti dalla Resource,
0 e 0 dopo il `table()` di pagina. Dopo: 6 e 3. Verificato su entrambi gli stati.

Ma la rimozione ha un rovescio: **tutti gli hook di tabella dichiarati sulle List
page sono diventati codice morto nello stesso istante**, e nessuno li ha spostati.

## Ampiezza (misurata 2026-09-08, non stimata)

Su 153 List page:

| Hook dichiarato sulla pagina | File |
|---|---|
| `getTableColumns()` | 90 |
| `getTableFilters()` | 35 |
| `getTableActions()` | 21 |
| `getTableBulkActions()` | 14 |
| `getTableHeaderActions()` | 3 |
| `table()` | 1 (`Progressioni/ListCedDiffs`) |

Nota sul falso positivo: `Incentivi/ListDefaultActivities` sembra ridichiarare
`table()` a un grep, ma il metodo e' **commentato** (riga 77). Non inseguirlo.

Delle 90 con `getTableColumns()`, costruendo la tabella reale e confrontando le
chiavi dichiarate con le colonne vive:

- **52 OK** — la Table class ha già tutto: il metodo sulla pagina è duplicato
  morto, si cancella.
- **36 con scarto** — chiavi dichiarate che non compaiono fra le colonne vive.
  ⚠️ **Il confronto per chiave ha falsi positivi noti**: se la Table class usa
  `ValutatoreSelectColumn::make()` senza argomento, il nome della colonna non
  coincide con la chiave dell'array della pagina. Vanno guardate **una per una**,
  non chiuse in blocco. I casi con scarto grosso e sicuramente reale:
  `Job/ListImports` (10 chiavi → 3 colonne), `Job/ListJobsWaiting` (12 → 3),
  `Job/ListSchedules` (10 → 3), `Media/ListMediaConverts` (15 → 3),
  `User/ListProfiles` (7 → 3), `Xot/ListLogs` (6 → 3).
- **3 rotte a runtime** fra queste 90 (5 in tutto il repo, vedi aggiornamento sotto):

| Pagina | Errore | Causa reale |
|---|---|---|
| `Job/.../ListJobBatches` | `Webmozart\Assert\InvalidArgumentException: [36][ListJobBatches]` | `JobBatchResource::$model` è **commentato** (riga 19), quindi `getModel()` non risolve. In più `JobBatchResource/Tables/` contiene **due** classi, `JobBatchesTable.php` e `JobBatchsTable.php`: `getTableClass()` usa `Str::plural()` e ne prende una sola, l'altra è un doppione da eliminare |
| `Media/.../ListTemporaryUploads` | `SQLSTATE[42S22]: Unknown column 'folder'` | un filtro fa `select distinct folder from temporary_uploads` su una colonna che non esiste |
| `Progressioni/.../ListCedDiffs` | `Livewire\Exceptions\PropertyNotFoundException: Property [$layoutView] not found` | ridichiara `table()` sulla **pagina** e legge `$this->layoutView`, proprieta' che arrivava da `HasXotTable` e non esiste piu' da `23965cd0b`. Segnalata dalla sessione `base-ptvx-fila5-be`, assorbita qui da 18.29 su sua richiesta: e' la **terza forma della stessa violazione** — l'UI su una pagina invece che sulla Table class — e la guardia che la ferma e' quella di questa story, non un fix isolato |

Inoltre **4 Resource non hanno affatto la cartella `Tables/`**: per quelle la
rimozione dell'hook di pagina va fatta solo dopo aver creato la Table class.

### Aggiornamento: le liste rotte sono 5

Il conteggio iniziale guardava solo le 90 pagine che dichiarano `getTableColumns()`.
Costruendo la tabella di **ogni** pagina che è davvero una `ListRecords`:
**142 costruiscono, 5 falliscono**.

⚠️ Una misura intermedia diceva 13: era sbagliata, e vale la pena sapere perché.
La sonda passava per `makeTable()` su qualunque `Pages/*.php`, e le 8
`*LogActivities` non ce l'hanno — non sono liste Filament, sono pagine custom.
Otto `ReflectionException` scambiate per otto bug. **Il filtro
`is_subclass_of($class, ListRecords::class)` è quello che rende la misura vera**;
senza, si conta il proprio strumento.

| Pagina | Errore | Famiglia |
|---|---|---|
| `Job/ListJobBatches` | `[36][ListJobBatches]` | `$model` commentato + Table class doppia |
| `Media/ListTemporaryUploads` | `Unknown column 'folder'` | filtro su colonna inesistente |
| `Progressioni/ListCedDiffs` | `Property [$layoutView] not found` | `table()` sulla pagina |
| `Ptv/ListCategoriaPropros` | `Expected a sub-class of XotBaseResourceTable` | risoluzione Table class |
| `Ptv/ListStabiDirigentes` | `Expected an existing class name` | risoluzione Table class |

Le ultime due, più `ListJobBatches`, sono la stessa famiglia: la Table class che
`getTableClass()` risolve non è quella che qualcuno credeva. Trattata a parte in
**story 18.31**, perché è un problema di naming e non di hook morti.

Comando per rimisurare (nessuna scrittura, solo costruzione):
istanzia ogni List page concreta, chiama `makeTable()` via Reflection e poi
`table()`, conta le eccezioni.

## Task

1. **Prima le tre liste rotte** (`ListJobBatches`, `ListTemporaryUploads`,
   `ListCedDiffs`): sono fuori uso adesso, non è debito, è un guasto.
   - `JobBatchResource`: riattivare `$model`, eliminare la Table class doppia.
     Il nome corretto e' **`JobBatchesTable`**: `getTableClass()` fa
     `Str::plural(class_basename(getModel()))`, quindi il nome si deriva dal
     **model** (`JobBatch` → `JobBatches`), mai dalla Resource — `JobBatchsTable`
     non e' raggiungibile da nessun percorso. Stessa regola per cui
     `PesisTable` e' stata rinominata `PesosTable` il 2026-09-08.
   - `ListCedDiffs`: il corpo di `table()` va nella Table class del suo Resource;
     `$this->layoutView` non si ripristina sulla pagina, e' la proprieta' del
     trait che non deve piu' stare li'.
   - `ListTemporaryUploads`: il filtro su `folder` va tolto o la colonna aggiunta;
     decidere guardando la migrazione, **mai** con una migrazione distruttiva.
2. **I 52 OK**: rimozione del metodo morto con tokenizer, mai regex — un
   `preg_replace` non ancorato ha già corrotto 21 file in una sessione e 2 in
   un'altra (vedi 18.19). `php -l` come gate per file.
3. **I 36 con scarto**: uno per uno. Il confronto affidabile è fra il **corpo di
   `getTableColumns()`** estratto col tokenizer e le colonne che la Table class
   produce davvero (`app($tableClass)->getTableColumns()`), non fra chiavi grezze
   del file. Dove la colonna manca davvero: **spostare** nella Table class, non
   cancellare.
4. **Gli altri hook** (`getTableFilters` 35, `getTableActions` 21,
   `getTableBulkActions` 14, `getTableHeaderActions` 3): stesso trattamento,
   stessa distinzione duplicato/da-spostare. `getHeaderActions()` sulla pagina
   **resta**: quello è di Filament e viene chiamato eccome — non confonderlo con
   `getTableHeaderActions()`.
5. **Le 4 Resource senza `Tables/`**: creare la Table class prima di toccare la pagina.
6. **Guardia** in `Modules/Xot/tests/Unit/Filament/`, accanto a
   `FormSchemaBelongsToFormClassTest.php`:
   - nessuna List page dichiara `getTableColumns/Filters/Actions/BulkActions/HeaderActions`
     **ne' `table()`** — quest'ultimo e' il caso `ListCedDiffs`, e senza la riga nel
     test il prossimo ripassa;
   - ogni Resource concreta ha esattamente una Table class e produce colonne non vuote;
   - **end-state**: ogni List page costruisce la propria tabella senza eccezioni e
     con almeno una colonna, **filtrando su `is_subclass_of(..., ListRecords::class)`**.
     Nessuna delle 5 fallisce l'analisi statica: falliscono solo costruendo.

## Definition of Done

- [ ] Le **5** liste rotte si aprono (le 3 di questa story; le 2 di risoluzione
      Table class le chiude 18.31)
- [ ] 0 hook di tabella dichiarati su List page, `table()` compreso
- [ ] Per ogni pagina toccata: o la colonna era già nella Table class, o ci è stata
      spostata — nessuna colonna persa, verificato per chiave sul corpo del metodo
- [ ] Guardia verde, inclusa la costruzione a runtime di tutte le List page
- [ ] PHPStan 0 sul toccato, nessun ignore, `phpstan.neon` intatto
- [ ] Nessuna migrazione distruttiva per il caso `folder` (dati sacri)

## Rischio da tenere d'occhio

È la stessa forma della trappola di 18.21: cancellare l'hook di pagina quando la
Table class è uno stub **non produce nessun errore**, la lista esce con meno
colonne e nessuno se ne accorge finché non lo segnala un utente. Il criterio
"esiste la Table class" non basta: conta il **contenuto**.
