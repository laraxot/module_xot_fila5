# XOT-5.43 — triage delle segnalazioni di `omniroute doctor`

## Story

Come manutentore della toolchain AI di questo repository, voglio che `omniroute doctor`
distingua i problemi veri dai falsi allarmi, cosi' da smettere di trattare dieci warning
come dieci lavori da fare quando quattro di essi non descrivono nulla di rotto.

## Contesto

`omniroute doctor` su OmniRoute 3.8.49 restituiva **7 ok, 10 warning, 0 failure**.
La domanda utile non era "come azzero i warning" ma "quali dei dieci descrivono
uno stato realmente degradato". La risposta, verificata leggendo il sorgente del
comando e non la sua stampa, e' che erano tre.

## Metodo di verifica

Ogni verdetto sotto e' stato ricavato leggendo il codice che emette il warning,
non interpretando il messaggio:

- `/usr/lib/node_modules/omniroute/bin/cli/commands/doctor.mjs`, funzione
  `checkNativeBinary` (righe 291-306)
- `/usr/lib/node_modules/omniroute/src/lib/cli-helper/tool-detector.ts`, costante
  `TOOLS` (righe 44-53) e funzione `isConfigured` (righe 72-79)
- `/usr/lib/node_modules/omniroute/bin/cli/commands/setup-continue.mjs`, funzione
  `buildContinueModels` (righe 50-68) e `categoriseModel` importata da `setup-codex.mjs`

## Dettaglio per ID

### D01 — porta 20128 gia' in uso

Il doctor controlla se la porta della dashboard e' libera. La porta e' occupata dal
server OmniRoute stesso (`ss -ltnp` la attribuisce al pid del processo
`omniroute (v16.2.12)`), che e' esattamente lo stato desiderato: il check subito dopo,
"Server liveness", conferma il server raggiungibile su quella stessa porta. Il warning
descrive il funzionamento normale come anomalia. Nessuna azione.

### D02 — better-sqlite3

Qui c'erano due cose distinte. La prima era reale: `omniroute runtime check`
riportava `{"installed":false,"valid":false}` e la directory di runtime non conteneva
il binario nativo. Risolta con `omniroute repair`, che ora produce
`~/.omniroute/runtime/node_modules/better-sqlite3/build/Release/better_sqlite3.node`.

La seconda e' un bug: `checkNativeBinary` cerca il `.node` solo sotto la root del
pacchetto npm (`/usr/lib/node_modules/omniroute/{app/,}node_modules/...`), mentre
`repair` lo installa nella runtime dir dell'utente. In una installazione npm globale
i due path non coincidono mai, quindi il warning resta acceso anche dopo una riparazione
riuscita. Vedi [bug upstream](./omniroute-doctor-upstream-bugs.md).

### D03 — Claude Code

`~/.claude/settings.json` conteneva solo tema e permessi: la segnalazione era corretta.
Configurarlo pero' significa scrivere `ANTHROPIC_BASE_URL` verso `localhost:20128`,
cioe' redirigere ogni sessione Claude Code, inclusa quella in corso.

Scelta presa: `omniroute setup-claude`, che genera 655 profili in
`~/.claude/profiles/<nome>/settings.json` usabili on demand via `CLAUDE_CONFIG_DIR`
o `omniroute launch --profile <nome>`, senza toccare `settings.json`. Verificato dopo
l'esecuzione che `settings.json` sia rimasto invariato.

Il warning resta acceso perche' il detector guarda solo `settings.json`. E' il costo
accettato della scelta, non un lavoro rimasto aperto.

### D04 — Codex CLI

Falso negativo. Il detector legge `~/.codex/config.yaml`; codex-cli 0.149.1 usa
`~/.codex/config.toml`, che in questa macchina contiene gia'
`base_url = "http://localhost:20128/v1"`. Scrivere un `config.yaml` per far tacere il
doctor produrrebbe un file che codex non legge: cargo cult, non un fix.

Nota collaterale emersa qui: codex-cli 0.149.1 ha rimosso il supporto a
`wire_api = "chat"` e rifiutava di partire. Corretto in `wire_api = "responses"`,
dopo aver verificato che il proxy espone `/v1/responses` (HTTP 200, risposta valida).
Backup in `~/.codex/config.toml.bak`.

### D07 — Kilo Code

Falso negativo, stessa forma di D04. Il detector legge
`~/.config/kilocode/settings.json`. Kilo Code 7.5.0 usa `~/.config/kilo` per la
configurazione e `~/.local/share/kilo/auth.json` per le credenziali, confermato da
`kilocode debug paths`. Quel file esiste gia' e punta a `http://localhost:20128/v1`.

### D06, D08, D11 — Cline, Continue, OpenClaw

Installate a livello utente con `npm install -g --prefix ~/.local`, perche' il prefix
npm di sistema e' `/usr` e `/usr/bin` non e' scrivibile senza password. `~/.local/bin`
era gia' primo nel PATH.

Prima di installare, ogni pacchetto e' stato verificato con `npm view`. Il controllo
non era una formalita': **due dei nomi ovvi sono pacchetti omonimi non correlati**.

| Nome cercato | Cosa c'e' davvero su npm | Usato |
|--------------|--------------------------|-------|
| `cline` | `github.com/cline/cline`, bin `cline` | Si' |
| `openclaw` | `github.com/openclaw/openclaw`, bin `openclaw` | Si' |
| `continue` | "Compose chainable async methods" di scottcorgan | No |
| `@continuedev/cli` | Continue CLI ufficiale, bin `cn` | Si' |
| `hermes` | "Messenger of the gods" di segmentio | No |

Configurazione: `omniroute setup-cline` per Cline. Per Continue,
`omniroute setup-continue` fallisce su questo catalogo (vedi bug upstream), quindi
`~/.continue/config.yaml` e' stato scritto a mano nel formato documentato da Continue,
con quattro modelli presenti davvero nel catalogo e il segreto referenziato via
`${{ secrets.OMNIROUTE_API_KEY }}` risolto da `~/.continue/.env` in permessi 600.
Per OpenClaw, che non ha un `setup-openclaw`, la configurazione e' stata applicata con
`openclaw config patch` e superata da `openclaw config validate`.

Il binario di Continue si chiama `cn`, non `continue`: aggiunto il symlink
`~/.local/bin/continue -> cn` perche' il tool e' effettivamente installato e il
detector cerca quel nome.

### D09, D10 — Hermes e Hermes Agent

Nessun pacchetto npm legittimo, ma il tool esiste: e' di Nous Research
(`github.com/NousResearch/hermes-agent`), distribuito dall'installer sul dominio del
vendor. Lo script e' stato scaricato e letto prima di eseguirlo: installa a livello
utente sotto `~/.hermes/hermes-agent`, senza sudo. Entrambe le voci del doctor puntano
allo stesso binario `hermes` (`defaultCommand: "hermes"` per tutte e due).

## Regola che questa story lascia al repository

Un warning di un doctor e' un'ipotesi, non un fatto. Prima di agire si legge il codice
che lo emette. Su dieci segnalazioni, quattro descrivevano il funzionamento corretto e
una descriveva una scelta gia' presa: agire su tutte avrebbe prodotto un `config.yaml`
inerte, un file in `~/.config/kilocode` che nessuno legge, e la redirezione non voluta
di Claude Code.

Corollario sui pacchetti: il nome ovvio su npm non e' il pacchetto giusto. `hermes` e
`continue` lo dimostrano. Si verifica `repository.url` e `bin` prima di installare,
sempre.

## Verifica

Stato di `omniroute doctor` prima e dopo, con il comando che lo riproduce:

```bash
omniroute doctor --no-color
```

- Prima: 7 ok, 10 warning, 0 failure
- Dopo: 12 ok, 5 warning, 0 failure

I cinque warning residui sono esattamente i cinque che questa story dichiara non
azionabili, uno per uno:

| Warning residuo | Perche' resta |
|-----------------|---------------|
| Port availability 20128 | D01, descrive il server sano |
| Native binary better-sqlite3 | D02, riparato davvero, path del check sbagliato |
| Claude Code non configurato | D03, scelta deliberata di non toccare `settings.json` |
| Codex CLI non configurato | D04, il detector legge `config.yaml` invece di `config.toml` |
| Kilo Code non configurato | D07, il detector legge `~/.config/kilocode` invece di `~/.config/kilo` |

Verifica funzionale aggiuntiva, oltre alla presenza dei file di config: una chiamata a
`POST /v1/chat/completions` con `model: auto/best-coding`, cioe' il modello usato nelle
config di Cline, Continue, OpenClaw e Hermes, risponde HTTP 200 e viene instradata su
`claude-opus-4-6-thinking`. I modelli scritti nelle configurazioni esistono davvero nel
catalogo.
