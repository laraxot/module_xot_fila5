# Story 18.19 — XotBaseResource: eliminare override illegali di metodi final

## Contesto (BMAD — fase Ricognizione)

Utente ha dichiarato la regola esplicitamente: chi estende
`Modules\Xot\Filament\Resources\XotBaseResource` NON deve avere il metodo
`getFormSchema()` (e per estensione `getFormSchemaOld()`, `table()`) perche'
sono dichiarati `final` nella classe base. Lo schema reale va in
`Schemas\{Model}Form::getFormSchema()` (che estende `XotBaseResourceForm`,
dove il metodo e' `abstract`, quindi obbligatorio) e in
`Tables\{Model}sTable::getTableColumns()` (estende `XotBaseResourceTable`).

Root cause del blocco repo-wide di PHPStan documentato in
`docs/chat/2026-09-07-URGENT-phpstan-bootstrap-fatal-ai-vs-xot-final-getformschema.md`
e nella memoria `project_xot_bootstrap_break_xotbaseresourceform_2026_09_07`
(3 occorrenze nella stessa giornata): lo swarm Epic4
(filament-canonical-structure) aveva gia' creato ovunque i gemelli
`Schemas/{Model}Form.php` e `Tables/{Model}sTable.php`, ma non aveva ancora
rimosso il vecchio override nella Resource originale in ~130 file su ~30
moduli. Dal momento in cui `getFormSchema()`/`table()` sono diventati
`final` in `XotBaseResource`, ogni file con l'override residuo fatalizza al
bootstrap — e Filament carica tutte le Resource di tutti i moduli per
costruire le route dei pannelli, quindi UN SOLO file cosi' rotto blocca
`phpstan analyse Modules` per chiunque, anche scoped a un modulo scorrelato.

## Approccio (fase Implementazione)

1. Audit repo-wide (`grep -rlE "class .* extends XotBaseResource\b"` +
   ricorsione sui discendenti indiretti come `LangBaseResource`,
   `BaseRatingResource`, `BaseRatingMorphResource`) per trovare ogni file con
   `getFormSchema()`, `getFormSchemaOld()` o `table(Table $table)` ridichiarati.
2. Per ognuno, verificato che il gemello (`Schemas/{Model}Form.php` con
   `getFormSchema()`, `Tables/{Model}sTable.php` con `getTableColumns()`)
   esistesse gia' con contenuto equivalente — solo allora rimosso
   l'override come dead code (mai perso schema/colonne: il contenuto vive
   gia' altrove).
3. Rimozione fatta con uno script PHP basato su tokenizer
   (non regex su stringa grezza — le regex su `.*?` non ancorate hanno
   backtrack e possono mangiare oltre il bersaglio, vedi incidente sotto),
   che rimuove modificatori + attributi (`#[\Override]`) + docblock +
   corpo del metodo in un solo blocco, con `php -l` come gate immediato
   per ogni file.
4. Nessun file senza gemello trovato tra le violazioni reali (i 2 casi
   Rating erano abstract base class con gemello annidato sotto la Resource
   concreta, non nella propria cartella — verificato a mano).

## Incidente in corso d'opera (da ricordare)

Un primo tentativo di ripulire gli attributi orfani con una regex
`preg_replace` non ancorata all'inizio ha "mangiato" la dichiarazione di
classe intera in 2 file (`TeamInvitationResource.php`,
`SocialiteUserResource.php` in User) perche' il quantificatore lazy fa
comunque backtrack in avanti se l'ancora finale fallisce, e con
`preg_match` senza `/A` la posizione di partenza piu' a sinistra vince anche
se richiede consumare molto piu' testo. Corretto tornando al tokenizer
(niente piu' regex su span di codice PHP) e ricostruendo i 2 file da
`git show HEAD:<path>` (mai un `checkout`, solo lettura storica) + editing
manuale mirato.

## Coordinamento multi-agente

Durante l'esecuzione, un altro agente (probabilmente lo stesso swarm Epic4,
working tree condiviso) ha fixato in tempo reale ~43/44 override di
`table()` e diverse decine di `getFormSchema()`/`getFormSchemaOld()`
(incluso il caso `LangBaseResource` → `Cms\AttachmentResource`) mentre
questa story era in corso — verificato via mtime identici su file di moduli
diversi (bulk script, non editing manuale) e via ri-grep che trovava "gia'
risolto" tra un mio comando e il successivo. Nessun conflitto di scrittura
rilevato (nessun file danneggiato da doppia scrittura simultanea).

**Addendum (sessione concorrente separata, stesso pomeriggio)**: un'altra
sessione ha lavorato in parallelo sullo stesso task partendo dalla stessa
richiesta utente, coprendo il residuo non ancora chiuso al momento del suo
avvio. Contributi non presenti sopra:
- `Modules/Rating`: `BaseRatingResource`/`BaseRatingMorphResource` sono
  abstract con un solo concrete consumer ciascuno (`RatingResource`,
  `RatingMorphResource`). Il check "esiste gia' un gemello Schemas?" cercava
  sotto `BaseRatingResource/Schemas/` (il nome della classe abstract) invece
  che sotto `RatingResource/Schemas/` (il nome della Resource concreta, che
  e' quello vero usato da `getFormClass()` via `static::class`) — falso
  negativo. Il gemello esisteva davvero: `RatingResource/Schemas/BaseRatingForm.php`
  (abstract, contenuto identico al vecchio `getFormSchema()` inline) +
  `RatingResource/Schemas/RatingForm.php extends BaseRatingForm {}` (vuoto,
  pattern Base/concrete che rispecchia `BaseRatingResource`→`RatingResource`),
  e `RatingMorphResource/Schemas/RatingMorphForm.php` gia' presente e corretto.
  Un primo tentativo ha sovrascritto entrambi con un'implementazione inline
  duplicata prima di accorgersi dell'errore (`git diff` contro HEAD mostrava
  contenuto pre-esistente, non un file nuovo) — corretto ripristinando i 2
  file al contenuto originale. Lezione: **verificare sempre `git show
  HEAD:<path>` prima di scrivere un file "nuovo" quando l'esistenza non e'
  stata controllata con il path esatto che il codice di produzione usa
  davvero** (qui: `{ConcreteResourceClass}\Schemas\{Model}Form`, mai il nome
  della classe abstract padre).
- Gotcha tokenizer aggiuntivo (vedi anche
  [[feedback_php_bulk_removal_tokenizer_not_regex]]): un commento a riga
  singola (`// ... l'apostrofo del table's ...`) contenente un apostrofo
  dentro `//` confonde un brace-matcher che traccia lo stato stringa
  carattere per carattere senza riconoscere `//`/`/* */` — l'apostrofo nel
  commento viene letto come apertura di stringa, il matcher salta ogni `{`/`}`
  reale fino alla fine del file (`NO_MATCH`). Fix: il matcher deve
  riconoscere ed ignorare `//` fino a fine riga e `/* ... */` PRIMA di
  tracciare `'`/`"` come stringa. Riscontrato su
  `Modules/Signage/app/Filament/Resources/SignCatalogItemResource.php`
  (commento `// components_count rides along from the table's counts()`).
- 2 bug collaterali non correlati alla regola ma bloccanti allo stesso modo
  (`#[\Override]` orfano su un metodo che non esiste nel parent, stesso
  identico pattern strutturale — attributo isolato seguito da un secondo
  docblock spurio prima del metodo): `Notify/NotifyThemeResource.php::fieldOptions()`,
  `User/OauthPersonalAccessClientResource.php::getTableColumns()`.
- Verifica indipendente: chiusura transitiva ricostruita da zero in Python
  (grafo `class X extends Y` via singolo grep + BFS in memoria, non un
  grep-per-classe in loop — quest'ultimo va in timeout su repo di questa
  scala), stesso esito: 0 violazioni reali residue, unico falso positivo
  `Blog/BannerResource.php` (`table()` gia' commentato).

- `php -l` su ogni file toccato: 0 errori di sintassi.
- Sweep finale repo-wide (`grep` su tutta `Modules/`, non solo primo

  `Filament/Clusters/*/Resources/*.php`): 0 violazioni residue di
  `getFormSchema()`, `getFormSchemaOld()`, `table(Table $table)` su
  discendenti (diretti o indiretti) di `XotBaseResource`.

  --memory-limit=-1` → **0 errori** (prima: PHP Fatal error in bootstrap).
- `./vendor/bin/phpstan analyse Modules --no-progress --memory-limit=-1`

  13417/43 moduli la mattina del 2026-09-07, prima di questo fix e del
