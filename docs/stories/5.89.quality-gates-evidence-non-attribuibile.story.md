# Story 5.89 — L'evidence dei gate non è di chi la legge

## User story

Come agente che esegue i quality gates in un repo dove lavorano decine di sessioni in
parallelo, voglio che il risultato che leggo sia **il mio**, perché oggi non posso saperlo.

## Il fatto, misurato

`bashscripts/docs/prompts/03-quality-gates.md` fa scrivere a ogni gate un file a **path fisso**:

```
build/pint.txt  build/phpstan.txt  build/phpstan-session.txt
build/pest.txt  build/phpmd.txt    build/insights.txt
```

Il prompt si apre dichiarando la premessa giusta — «in repo multi-agente la dirty list non è
la tua sessione» — e la applica al **preflight**, che scrive la dirty list in
`storage/app/ai/qg-dirty-$$.txt`, con il PID nel nome. Poi non la applica agli **output**.

Eseguito il 2026-09-09 con **17 processi PHPStan concorrenti** di altre sessioni:

| Ora | Cosa ho letto | Cosa stava facendo il mio processo |
|---|---|---|
| 11:15 | `build/pest.txt` con `Tests: 35 failed, 3 risky, 64 passed`, `Duration: 264.23s` | Pest **non ancora avviato** |
| 11:15 | `build/phpstan.txt` → `[OK] No errors` | PHPStan `Modules` **ancora in corso** |
| 11:21 | `build/phpstan.txt` riscritto, 3649 byte, 5 errori | il mio PHPStan aveva finito |
| 11:26 | il mio Pest va in **timeout** a 600 s → `pest=2` | `build/pest.txt` diceva ancora «completato in 264 s» |

Due esiti opposti dallo stesso file, a distanza di minuti.

## Perché conta, e non è un fastidio estetico

Chi legge `build/<gate>.txt` per decidere se il proprio gate è verde può leggere il risultato
di un altro. Il caso benevolo è perdere tempo. Il caso sfortunato è **dichiarare verde un gate
rosso** — o, peggio, mettersi a correggere codice che non si è rotti.

È lo stesso difetto di classe già visto altrove in questo repo: *un errore che non rompe niente
non si vede*. Nessuna eccezione, nessun log, un file che si legge benissimo e dice la cosa
sbagliata.

## Cosa è già attribuibile, e va detto

La riga machine-readable che il prompt fa stampare alla fine:

```
GATES pint=0 phpstan=1 phpstan_session=0 pest=2 phpmd=0 insights=0
```

è sullo **stdout del proprio processo**: quella è l'unica evidenza certa della propria
sessione, e **non finisce in `build/`**. Oggi il prompt la presenta come «riepilogo utile in
multi-agente / chat» — in realtà è l'unica cosa che regge in multi-agente.

## Acceptance criteria

- [ ] Gli output dei gate sono scritti in un percorso proprio della sessione — suffisso
      (`build/<gate>-${AGENT_SESSION}.txt`) oppure cartella (`storage/app/ai/<session>/`),
      coerente con quello che il preflight già fa per la dirty list
- [ ] I path fissi restano leggibili come «ultimo run» (copia o symlink), per non rompere chi
      li legge oggi
- [ ] Il prompt dichiara esplicitamente che `build/` è condiviso, come già fa per la dirty list
- [ ] Il prompt dice che la riga `GATES …` è l'unica evidenza attribuibile alla sessione
- [ ] Nessuna modifica a `laravel/phpstan.neon` (sacro, solo utente)

## Rilievo collegato — perché `Modules/Rating` non è chiudibile

Nello stesso run, `phpstan analyse Modules` ha dato **5 errori, nessuno della sessione**:

| Dove | Errore | Natura |
|---|---|---|
| `Ptv/app/Filament/Tables/Filters/HasRatingValuesFilter.php` | «File does not exist», `phpstan.path` | **falso positivo**: verificato, il file non esiste sul disco. Result cache stantia; rimedio documentato `clear-result-cache` |
| `Rating/tests/Unit/BaseRatingModelTest.php:38,40,41` | `linkedTo()` undefined, due `on mixed` | file **untracked** di un'altra sessione |
| `Rating/tests/Unit/ChildrenRelationManagerParentTest.php:58` | `$parent_id` undefined property | file **untracked** di un'altra sessione |

I quattro di `Rating` emergono perché **un path passato in CLI bypassa
`excludePaths: ./*/tests/*`** del neon — comportamento che il prompt stesso descrive per
`phpstan-session`, ma che vale anche per `analyse Modules/<Modulo>`.

Conseguenza operativa: la *definition of done* del prompt chiede
`phpstan analyse Modules/<Modulo>` a zero errori, ma **un modulo non è chiudibile da chi non
possiede i file rossi**. Serve una risposta esplicita: la DoD si valuta sui file della
sessione, o si aspetta che il working tree altrui sia pulito?
