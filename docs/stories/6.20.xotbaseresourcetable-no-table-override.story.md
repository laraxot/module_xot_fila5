# BMAD Story — XotBaseResourceTable Architecture Rule

## Understand
- **Problema**: Classi che estendono XotBaseResourceTable hanno metodo `table()` che causa errori
- **Regola architetturale**: Chi estende XotBaseResourceTable NON deve avere il metodo `table()`
- **Causa**: XotBaseResourceTable già definisce table() in modo standardizzato; overridding causa conflitti

## Audit 2026-09-07 — trovate 2 istanze reali + un bug gemello più grave

Lo sweep repo-wide (`find *Table.php sotto */Tables/ + grep "extends XotBaseResourceTable" + grep "function table("`)
ha trovato **2 violazioni reali** su tutto il repo:

| File | Violazione `table()` | Import FQCN | Severità |
|---|---|---|---|
| `Modules/Quotation/app/Filament/Resources/SiteSurveyResource/Tables/SiteSurveysTable.php` | Sì | **Rotto**: `use Modules\Xot\Filament\Tables\XotBaseResourceTable;` (namespace inesistente, manca `Resources\`) | **P0 — crash bootstrap** |
| `Modules/Media/app/Filament/Resources/MediaConvertResource/Tables/MediaConvertsTable.php` | Sì | Corretto | P2 — perde i default di `HasXotTable::table()` (recordActionsPosition, striped, filtersLayout, ecc.), ma non crasha |

**Scoperta collaterale più grave del `table()` override in sé**: `SiteSurveyResource` aveva
**3 file su 3** (`Schemas/SiteSurveyForm.php`, `Schemas/SiteSurveyInfolist.php`,
`Tables/SiteSurveysTable.php`) con lo **stesso identico bug strutturale a 3 facce**, probabilmente
da un'unica generazione AI mai verificata a runtime:
1. `use` verso un FQCN del tutto inesistente (`Modules\Xot\Filament\Resources\XotBaseResourceForm`
   invece di `Modules\Xot\Filament\Resources\Schemas\XotBaseResourceForm`; stesso pattern per
   Infolist e Table con varianti diverse dell'errore — vedi tabella).
2. Override del metodo astratto/final del genitore con visibilità **non-static** mentre il
   contratto lo vuole `public static` (`getFormSchema()`, `getInfolistSchema()`) — un secondo
   errore fatale indipendente, mascherato dal primo perché la classe non arriva mai a caricarsi.
3. Una `protected static string $resource = ...` inutile, mai letta da nessun consumer (verificato
   con grep — il pattern reale di Filament per `$resource` vive solo nelle classi `Pages\*`, non
   nelle `Schemas\`/`Tables\`).

**Perché è più grave di un gap "cartella mancante"**: qui le cartelle `Schemas/`+`Tables/` ESISTONO,
sembrano conformi a un controllo superficiale (story 4.3 lo avrebbe classificato "OK", 0 gap) — ma
la classe non arriva mai a caricarsi. `class_exists()` in `XotBaseResource::form()`/`getTableClass()`
non intercetta l'errore: quando l'autoloader prova a risolvere `extends XotBaseResourceForm` verso
un FQCN inesistente, PHP solleva un **Error non catchable da `class_exists()`** — la risorsa crasha
a runtime (500) alla prima navigazione, e la stessa classe rotta fa fallire il bootstrap dei panel
Filament per **l'intero monorepo**, non solo per Quotation: `discoverResources()` di Filament
richiama `class_exists()` su ogni Resource di ogni modulo installato durante il boot dell'app, quindi
anche `phpstan analyse Modules/<qualsiasi-altro-modulo>` fallisce con "Application bootstrap failed"
finché questo singolo file non è corretto — bloccava OGNI agente su OGNI modulo in questa sessione.

**Non è un checklist coverage gap**: `filament_audit.sh` (story 4.3) verifica solo
esistenza-cartella + grep su `function getFormSchema`/`function table(` sul file **Resource**, non
verifica che le classi dentro `Schemas/`/`Tables/` si carichino davvero né che i loro override
abbiano la firma giusta. **Da aggiungere allo script**: un check `php -l` + un tentativo di
`class_exists()` reale (via `artisan tinker` o un comando dedicato) per ogni classe trovata.
