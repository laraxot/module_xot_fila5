# 10. PHPStan fatal crash fix: final-method override + Devin collision

Status: done
Date: 2026-09-08

## Contesto

Richiesta utente: sistemare tutte le segnalazioni PHPStan in parallelo
(swarm/subagents/BMAD/second brain). `./vendor/bin/phpstan analyse` sull'intero
`Modules/` non arrivava nemmeno a produrre un report: crash PHP fatale a
`0/7754` file, prima di qualunque analisi statica.

## Causa radice

Due varianti dello stesso bug architetturale, gia' noto e documentato in
`bashscripts/ai/.agents/rules/form-schema-lives-on-form-class.md`:

1. `XotBaseResource::getFormSchema()` e `::form()` sono `final`. Diverse
   Resource (`ClientResource`, `PhoneCallResource`, `MedicalDirectorResource`,
   ... in TechPlanner; `FailedJobResource`, `JobBatchResource`,
   `JobManagerResource`, `ExportResource`, `JobsWaitingResource`,
   `ScheduleResource`, `FailedImportRowResource`, `ImportResource`,
   `JobResource` in Job; `DomainResource` in Tenant) le ridichiaravano —
   `Cannot override final method` e' fatale PHP a compile-time, non un errore
   PHPStan qualsiasi: blocca l'intero autoload/bootstrap.
2. `XotBaseViewRecord`/`LangBaseViewRecord` non dichiarano mai
   `getInfolistSchema()` (il vero hook e' `XotBaseResource::infolist()`,
   final, che delega a `{Resource}\Schemas\{Model}Infolist`). Diverse pagine
   `ViewXxx` (TechPlanner, Cms) marcavano comunque `#[Override]` su un
   `getInfolistSchema()` di pagina — mai chiamato da nessuno, ma
   `#[\Override]` senza metodo parent corrispondente e' anch'esso fatale in
   PHP 8.3.

In entrambi i casi il vero schema vive gia' nella classe
`{Resource}\Schemas\{Model}Form` / `{Model}Infolist` (pattern
`XotBaseResourceForm`/`XotBaseResourceInfolist`, `getFormClass()`/
`getInfolistClass()` per convenzione di naming) — la ridichiarazione su
Resource/Page era sempre codice morto irraggiungibile.

## Collisione multi-agente scoperta durante il fix

Mentre si applicava il fix, gli stessi file venivano riscritti in tempo reale
da un secondo agente (Devin, via Windsurf, processo `devin acp` attivo sulla
stessa working copy — non visibile a `ListAgents`, che vede solo sessioni
Claude Code). Evidenza: `git diff` su file appena letti che cambiavano tra un
tool call e l'altro; `ps aux` con `devin acp` + `windsurf` language server in
esecuzione.

L'estrazione automatica di Devin per 4 classi Form ha **perso campi reali**,
collassandoli in uno stub `Section::make(['name' => TextInput::make('name')])`:

| Resource | Campi originali | Campi rimasti nello stub |
|---|---|---|
| `ExportResource` | name, type, status, error_message, created_at, updated_at (6) | name (1) |
| `JobsWaitingResource` | job_id, name, queue, started_at, finished_at, failed, attempt, exception_message (8) | name (1) |
| `ImportResource` | name, file, status, error_message, total_rows, processed_rows (6) | name (1) |
| `JobManagerResource` | job_id, name, queue, started_at, finished_at, failed, attempt, exception_message (8) | name (1) |

PHPStan non rileva questo tipo di regressione (l'array e' comunque
tipizzato correttamente) — solo lettura/confronto manuale col codice
originale l'ha trovata. Riscritto due volte: la prima riscrittura e' stata
sovrascritta a sua volta dal processo Devin (mtime tornato a un file datato
2026-09-07), la seconda ha retto.

Rimosso anche un file duplicato spurio:
`Modules/Xot/Filament/Forms/Components/XotBasePlaceholder.php` (fuori da
`app/`, stessa FQCN della classe reale in `Modules/Xot/app/Filament/...`,
untracked) — probabile artefatto della stessa corsa concorrente.
