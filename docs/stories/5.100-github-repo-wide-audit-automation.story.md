## Contesto

Regola esistente ([[spiegare-ogni-modifica-su-github]], memoria 2026-09-09) verifica, via
pre-commit hook sulla root, che ogni story BMAD in stage abbia link `/issues/<n>` e
`/discussions/<n>` nel frontmatter. Copre: *"il mio lavoro ha un link?"*.

Non copre: *"ho controllato se ci sono issue/discussion GIÀ aperte nella repo del modulo,
correlate al lavoro appena fatto ma non create da me in questa sessione?"*.

Gap trovato lavorando sul modulo Rating in questa sessione: le issue #53 ("docs:
RatingResource reorderable adoption") e #54 ("Rating reorderable pattern - design review")
erano aperte da lavoro precedente, direttamente correlate al reordering implementato,
e non erano mai state controllate finché l'utente non lo ha segnalato esplicitamente.
Root cause completa: [[github-repo-wide-interaction-mandatory]].

## Deliverable

Script bash in `bashscripts/tools/github/` (root-script-policy: niente `.sh` in root) che:

1. Riceve un path di modulo come argomento
2. Esegue `cd <path> && git remote -v`, sceglie `laraxot` se esiste, altrimenti l'altro
   remote disponibile (stesso criterio già in uso manualmente in questa sessione)
3. Esegue `gh issue list -R <repo> --state open --limit 100`
4. Esegue `gh api repos/<repo>/discussions --paginate` (con fallback silenzioso se il
   repo ha le discussion disabilitate — vedi nota sotto)
5. Stampa un report leggibile: numero, titolo, url, per issue e discussion

## Nota — discussions non sempre disponibili

Verificato in questa sessione: `provtv/module_xot_fila5` ha le issue abilitate ma le
discussion disabilitate (`gh api repos/provtv/module_xot_fila5/discussion-categories`
→ 404). Lo script deve gestire questo caso senza fallire — riportarlo nell'output come
"discussions disabled for this repo", non come errore bloccante.

## Criteri di accettazione

- [ ] Script eseguibile con un solo argomento (path modulo)
- [ ] Sceglie il remote corretto secondo la convenzione (laraxot > altri)
- [ ] Report leggibile, non JSON grezzo
- [ ] Gestisce discussions disabled senza fallire
- [ ] Test Pest o shell test che verifica l'output su un repo noto (TDD, come da standing
      order)
- [ ] Invocato manualmente prima del report finale finché non diventa hook automatico
      (l'automazione completa — hook che blocca il report — è fuori scope di questa story,
      valutare in una story successiva se il costo/beneficio regge)
