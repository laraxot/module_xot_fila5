# Story 18.34 — Moduli e script agnostici dal progetto ospite

## Il fatto

`laravel/Modules/`, `bashscripts/` e `docs/` sono condivisi fra piu' progetti. Nessun
modulo si chiama come i progetti che li usano, quindi **ogni** occorrenza di quei nomi e'
un residuo importato. Misura del 2026-09-08, esclusi `vendor/` e `node_modules/`:

| | `.php` | `.sh` | `.md` |
|---|---|---|---|
| prima | 31 | 55 | ~3.300 |
| dopo (questa sessione) | **0** | 54 | ~3.300 |

## Perche' non e' una questione di stile

Tre danni misurati, non ipotetici:

1. **`Schema::connection('<progetto>')`** in `UserBusinessLogicTest`: quella connessione
   non esiste in questo checkout. Il ramo di skip non e' mai girato — il test sembrava
   passare e non verificava niente.
2. **`database_path('<progetto>_data.sqlite')`** cablato in 12 `TestCase`: la suite di
   ogni modulo pretendeva il file di un progetto specifico. In `Rating` il nome cablato
   era addirittura un terzo (`database.sqlite`), quindi puntava a un file inesistente:
   trovato dalla guardia, non dal `grep` — il `grep` cercava il nome noto.
3. **`cittadino@<progetto>.demo`** in `DemoUserSeeder`, dentro il modulo User condiviso:
   dati di dominio di un altro progetto.

## Cosa e' stato fatto

`XotBaseTestCase::sharedSqlitePath()` e' ora la sola sorgente del path, e lo risolve in
tre passi dal piu' esplicito al piu' neutro:

1. `config('xot.testing.sqlite_file')` — il progetto dichiara il proprio file;
2. l'unico `*.sqlite` presente in `database/` — il caso normale, funziona senza
   configurare niente e qualunque nome il progetto scelga;
3. `test_data.sqlite` — default neutro.

Retrocompatibile: con un solo file in `database/` il passo 2 trova quello di oggi.
Rinominato anche `prepareShared<Progetto>SqliteForTesting()` → `prepareSharedSqliteForTesting()`
(8 chiamanti aggiornati, nessun alias: due nomi per lo stesso metodo sono l'anti-pattern
di 5.46).

## Guardia

`Modules/Xot/tests/Unit/Docs/ModuleCodeIsProjectAgnosticTest.php`, **soglia zero** — non
un tetto decrescente: il codice e' pulito adesso, quindi l'asserzione puo' essere secca.
Due test: nessun `.php` di modulo nomina un progetto ospite, e nessuno ricabla un nome di
file sqlite. Verificata: aggiungendo un file con quel nome fallisce.

Affianca `ModuleDocsAreProjectAgnosticTest`, che copre i `.md` con un tetto decrescente
perche' li' il debito e' di migliaia di file.

## Cosa resta

- **54 script `.sh` in `bashscripts/`.** Nessuna guardia li copre. Vanno guardati uno per
  uno: alcuni saranno path di deploy di un progetto specifico, e quelli non vanno resi
  agnostici ma **spostati fuori** da `bashscripts/` condiviso.
- **~3.300 documenti `.md`.** Coperti dal tetto decrescente, quindi non peggiorano.
- **`database/<progetto>_data.sqlite`**: il file esiste ancora con il nome vecchio. Ora e'
  irrilevante per il codice (viene trovato per estensione), ma rinominarlo in
  `test_data.sqlite` chiuderebbe il cerchio. Da fare quando nessuna sessione sta girando
  test: e' il file su cui si appoggia tutta la suite.

## Acceptance criteria

- [x] 0 riferimenti nel codice `.php` dei moduli
- [x] Il path del database di test non e' cablato in nessun modulo
- [x] Guardia a soglia zero sul codice, verificata su una violazione
- [x] PHPStan 0 sui file toccati
- [ ] 54 `.sh` esaminati: resi agnostici o spostati fuori da `bashscripts/`
- [ ] Guardia estesa agli `.sh`
- [ ] File sqlite rinominato in modo neutro

## Nota

La misura iniziale per `grep` diceva 31 file `.php`. La guardia ne ha trovato uno in piu'
(`Rating/tests/TestCase.php`) perche' cercava la **forma** — `database_path('*.sqlite')` —
invece del nome noto. Cercare il nome trova quello che gia' sai; cercare la forma trova
quello che non sai. Vale per la bonifica degli `.sh`: cercare i nomi dei progetti ospiti — l'elenco vive in
`forbiddenProjectNames()` dentro la guardia — non bastera'.

## Il fatto

Un modulo e un tema sono pacchetti **riusabili**: lo stesso `Modules/Xot` gira in
più progetti. `bashscripts/` è un repo condiviso fra progetti. La loro
documentazione deve valere in tutti, quindi non può nominare nessuna installazione
specifica.

Misurato il 2026-09-08:

| Area | File | Occorrenze |
|---|---|---|
| `laravel/Modules/*/docs/` + `laravel/Themes/*/docs/` | **1.642** | ~10.600 |
| `bashscripts/` (`.md` + `.sh`) | — | ~7.400 |
| `docs/` (radice del repo) | — | ~170 |

Le occorrenze in `docs/` alla radice sono in gran parte **legittime**: quella
cartella è la cronaca di *questa* installazione. Il problema è nelle prime due aree.

## Perché conta davvero, e non è pedanteria

Una frase che nomina l'installazione non è "meno elegante": è **falsa** ovunque
tranne che lì, e nessuno se ne accorge finché il modulo non viene riusato — a quel
punto la documentazione dice al lettore cose che non trova nel suo progetto. Il
danno è ritardato e silenzioso, come tutte le rotture che questa giornata ha
prodotto.

C'è anche un effetto composto: un agente che apre i docs di un modulo e ci trova
il nome di un'installazione **impara che si fa così**, e lo replica. È lo stesso
meccanismo per cui 94 file su 164 in `docs/chat/` hanno la data nel nome. Il debito
di documentazione si autoalimenta perché è il campione da cui si impara.

## Cosa è già fatto

- `docs/wiki/rules/project-agnostic.md` **riempito**: prima era un anello vuoto che
  linkava se stesso (vedi story `18.34`). Ora dice cosa è vietato, dove vale, e
  come si riscrive una frase specifica senza perdere l'informazione.
- Guardia `Modules/Xot/tests/Unit/Docs/ModuleDocsAreProjectAgnosticTest.php`: tetto
  a 1.642 file, può solo scendere. Non pretende zero — impedisce che il numero salga.
- Corretta l'unica occorrenza introdotta oggi (story `18.33`).

## Task

1. **Bonifica per valore, non alfabetica.** Prima i file che qualcuno legge davvero:
   `README.md` dei moduli, `docs/index.md`, le regole del wiki. Un file di archivio
   con 40 occorrenze conta meno di un README con una.
2. **Riscrivere, non censurare.** Il dettaglio si sposta dove è vero:
   «la fixture `<nome>_data.sqlite`» → «una fixture SQLite fornita dal progetto
   ospite; il nome sta nella configurazione». La forma agnostica dice la **regola**
   invece dell'accidente, ed è più utile, non meno.
3. **Abbassare il tetto a ogni giro.** Un ratchet che non scende torna verde per
   inerzia e smette di misurare.
4. `bashscripts/` ha un tetto suo da fissare: è un repo separato, condiviso fra
   progetti, e va misurato prima di toccarlo.
5. Le occorrenze in `docs/` alla radice vanno **classificate**, non bonificate in
   blocco: lì nominare l'installazione è spesso corretto.

## Definition of Done

- [ ] Nessun file nuovo aggiunge occorrenze (già garantito dalla guardia)

solo di **documentazione**. Il codice che legge un nome dalla configurazione è
già corretto.
